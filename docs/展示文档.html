  1. 真实流程：在指定普通笔记本上，深蹲和开合跳各连续完成至少 3 个全流程（设置→真实训练→报告→提案→确认→新组），记录失败次数；模拟只能兜底。

样本、真值与分组

  1. 建议 8–12 名自愿成年人；缩减时至少 5 名，每动作每人 2 个正常组，每组 10 次。另采静止、局部遮挡、出画、错误机位、中途起录、暂停恢复、漏帧/低帧率。只在本人舒服的范围完成动作，不要求危险姿势。
  2. 用 P01/P02 等匿名编号，按人划分调参/验证/最终测试，组员复核划分；同一视频的相邻片段不可跨划分。原始视频及可识别信息不入仓库，是否保留影像由参与者选择。
  3. 首标人员在不知道预测次数的情况下数完整周期；第二人复核。保留争议，先裁定再评测，不能根据预测结果改真值。两个复核 ID 必须不同。
  4. count_eligible=true 表示具有可人工计数真值的有效完整组；false 必须写 exclusion_reason。拒绝组照常进入报告，列出预测次数和门控结果。未标注为 null，MAE 不计算。不能为了降低 MAE 剔除算法失败组；只有真值不可确定或不符合预定采集协议时才排除，并单列原因。
  5. quality 标签 observed=该动作在此机位与可见性下可评价；unknown=缺点、遮挡、出画、错误机位或无法确定。静止正常站立可为 observed，但 expected_activity=rest。活动状态 work/rest/unknown 是视觉运动标签，不是代谢强度。
  6. 深蹲可额外标 reference_cycles：结束时间 end_ms、实验幅度 rom、下降/上升阶段秒数。仅标可人工判断的字段，不清楚的幅度用 unobservable，阶段时长留空。回放以结束时刻 ±500 ms 一对一匹配，并报告未匹配周期，避免只展示匹配成功样本。

问题与产品闭环

居家新手常缺少及时动作反馈，也不清楚疲劳后是否应调整下一组。LocalFit 使用本机摄像头/视频形成有限动作证据，结合用户自报疲劳和不适生成下一组提案，经用户确认才应用。原始影像不进入后端摘要接口，规则输出附版本、依据和状态记录。

主线只验证深蹲与开合跳；其余 28 项是实验目录。饮食为可确认份量的示例食物计算，原创骨架为示意外观。这些辅助模块不能代替核心可靠性证据。

全流程健康教练适合赛道一，但原始设想包含动作识别、卡路里、不同体型、多模态、饮食、动作纠正、端侧隐私等多个高难度方向。参赛版应收敛为面向居家健身新手的端侧 AI 教练，核心是：离线动作纠正＋基于训练表现调整计划；饮食是闭环补充，广泛健康管理属于赛后路线。

4. 动作技术路线

先从侧面深蹲和正面开合跳开始。用户先选择动作，系统识别动作阶段、次数和质量，降低开放式识别难度。

处理链：关键点 → 时间平滑 → 视角与可见性检查 → 动作阶段状态机 → 次数 → 可观察偏差 → 带依据提示。

MediaPipe Pose Landmarker 输出 33 个人体关键点及可见性，支持网页视频。它不是动作纠正引擎，纠错需要自己设计与验证。检测同步调用可能阻塞主线程，采用 Web Worker。单目三维估计不能当作精密运动测量。

侧面深蹲可观察幅度、节奏、躯干倾斜趋势；膝内扣更依赖正面。每个机位限定评价能力。提示应表达证据，例如“本组下降幅度比校准动作小”，避免仅给不透明综合分。

“不同体型”通过躯干等比例尺度归一化、个人初始基线、训练历史体现，不从视频推断真实体重或身体健康。校准本身可能不规范，不能自动当作正确动作标准。需区分机位偏差、遮挡、模型误差与动作问题；按体型、衣着、光照报告验证结果。

当前代码是规则基线：深蹲左侧髋膝踝角度的双阈值计数、可见性门控、倾斜提示；开合跳按手臂和脚距状态计数。自动机位判断与个体校准尚未完成。关键点可见性不是纠错正确率。

有足够标注和明确错误模式后可训练小型 TCN/GRU 时序模型，对比规则基线；ONNX Runtime Web 端侧部署。按用户划分训练、验证、测试集，避免同人相邻片段泄漏。

5. 消耗估算与饮食

基础公式：总消耗 kcal ≈ Σ MET × 体重 kg × 时长小时。按运动和休息分段，标记是否含静息消耗；如输出净活动消耗，应另作计算和明确说明。动作识别帮助选择活动类别，节奏、自评强度可形成估算情景，但没有数据不能宣称动作幅度准确预测能量。

Compendium 官方指出 MET 表不是为了精确测量个体活动能耗而设计；个体能耗、静息代谢存在差异。范围应标“假设下的情景范围”，没有统计校准不能称 95% 置信区间。无间接测热等真值，不报卡路里预测准确率。参考：定义、个体限制。

当前代码 MET 值是演示假设，不是完整活动条目映射。后续需每个动作绑定来源 ID、活动描述、参数版本和适用条件。

饮食先做手动食物选择＋确认克数＋数据库计算。可研究 USDA FoodData Central，补充中国食物、烹饪与配方覆盖；记录食品 ID、来源、每 100g 营养、版本和使用许可。模型只解释查表结果，不编造数值。不把运动消耗机械等价为可多吃多少。一般建议可引用 WHO 健康饮食资料。当前 4 条食物数值是未核验演示条目，不提供完整饮食处方。

6. 架构与算力安排

推荐浏览器实时感知＋同机 FastAPI Agent 服务。React/TypeScript/Vite 页面、Canvas 骨架、MediaPipe Worker、动作状态机、结构化摘要、本地 SQLite。主界面不等待语言模型逐帧决策。

普通笔记本是最终验收设备：姿态、计数、纠错、计划调整必须本地可完成。4090 用于开发、模型评测和较大模型对照；A100 用于有价值的小模型训练，不必为用算力训练大模型。若 4090 远程运行并接收摘要，该模式必须另标远程增强，不能称全部端侧。

可选 llama.cpp＋量化中文小模型，先试 Qwen3-4B，再根据实际速度和内存缩小。当前适配器仅连接同机回环地址、只解释已有结果，不执行计划。模型权重不提交 Git。LangGraph 适合混合确定性与模型步骤，作为后续替换当前轻量编排器的实现项。

1. 动作识别：先区分三件事

姿态估计回答关键点在哪里，类别识别回答正在做什么，阶段分析回答该动作完成到哪一步。上游训练示例和当前 LocalFit 都主要针对已选动作分析，不是通用活动分类器。

比赛先由用户选择动作，系统验证机位和完整周期。自动类别识别未来可基于关键点时序小模型，必须包含 idle/unknown，避免把整理衣服或弯腰误认为训练。先用标注回放验证误识别，再扩充第三动作。

2. 次数、幅度和正确性分开

上游 pull_ups 独立记录次数和幅度，浅动作也可以计数，再评价两端幅度。LocalFit 采用独立实现的深蹲基线：先见到站立区间再启动候选周期，用下降/返回双区间完成计数，再按当前实验阈值记录幅度。

本次实现 within_rule / below_rule / unobservable 三态，分别表示达到实验幅度、未达到、不可评价。它们不等于动作安全/危险或生物力学正确。上游某些不可见端点按未达标处理，我们保留 unknown 状态，避免把检测失败归因于用户。

逐次记录开始、最低点、结束、下降和起身耗时、最低角度与幅度状态，界面与后端报告保留最近 100 次。开始时间是进入实验角度区间后的时间，不是精确运动起始点；平滑会影响极值和节奏，必须通过标注验证。暂停不进入活动时钟；超过 500ms 观察缺口丢弃未完成候选，不能在长缺口插值后强判。

3. 宽高比是实际修正项

MediaPipe x/y 分别按画面宽高归一化，不能直接当成相同长度单位算角度。此次 jointAngle 先把 x 差乘画面 width/height，再求二维角度。Worker 回传实际 ImageBitmap 的宽高比；躯干水平/垂直比也校正。

这解决非方形画面的几何尺度问题，不解决单目投影、摄像头方向或关键点偏移。上游 COCO-17 与我们 MediaPipe-33 的编号不同，后续替换姿态模型必须显式映射，不能直接按数组下标接入。

关键映射参考：COCO shoulder 5/6 → MediaPipe 11/12；elbow 7/8 → 13/14；wrist 9/10 → 15/16；hip 11/12 → 23/24；knee 13/14 → 25/26；ankle 15/16 → 27/28。缺失的额外关键点必须标不可见；COCO score 不应未经验证等同 MediaPipe visibility。

4. 校准应绑定用户、动作与机位

5. 实时与离线算法不能直接互换

上游部分计数采用居中滤波、完整片段幅度统计和插值，这些可能读取未来帧或整段数据。适合离线回放，不能直接声称实时无延迟。我们的当前引擎采用因果平滑、已有历史和缺口拒绝；后续保存原始摘要用于组后更精细复盘。平滑系数仍按帧，跨 FPS 可比性待改成按时间参数并评测。

建议做对照：同一授权回放 → MediaPipe 本地姿态 → 实时规则；可选 4090 本地 ViTPose → 同一归一化接口 → 同一规则。比较关键点失败、计数、误报、时延与资源，不仅比较演示观感。没有需求授权时，不调用上游云端 API 上传真实用户视频。

6. 卡路里计算保持独立模块

本次源码与说明的关键词核查未找到 calorie/kcal/能耗模型，因此不能写“已接入该项目的热量算法”。逐次节奏能帮助分段或查强度，但仅凭姿态、次数或相似度无法精确推断个体代谢；负荷、体重、肌肉募集和生理反应都会影响结果。

路线：动作/强度映射 → 区分训练和休息时长 → 用户体重 → MET 场景 → 总/净消耗及不确定性说明。运动总 kcal 约为 Σ MET×kg×小时；净活动消耗需扣除同时间静息口径。可穿戴心率只能作为辅助，不是无误差真值。无测量真值不报告能耗准确率。

当前后端仍按运行活动时钟和演示 MET 区间估算，尚未自动分出站立/休息，原地停留可能高估。此次单次时间数据是后续分段的基础，不能直接把候选周期时长当作全部运动生理时长，也不能用次数×固定 kcal。

模块边界

  • 摄像头原始帧仅在浏览器主线程与同源 Worker 间传递，不发送后端。
  • Worker 只提取姿态；动作引擎独立可测试，不依赖 React。
  • 前端累计实际活动时长与最近有效姿态覆盖时长；暂停不计时；长时间追踪丢失重置动作阶段，避免跨缺口计数。
  • 后端仅接收有限字段摘要，不接收视频、音频或关键点数组。
  • 规则协作形成候选计划；用户确认才能更新目标；不适提案禁止确认。
  • LLM 仅解释已有提案，不能写状态。异常或未启用时用规则解释降级。
  • 默认同机单用户、单进程。没有认证、多人隔离或跨进程锁，不可直接暴露公网。

状态与合同

训练状态：ready → running ↔ paused → summarized → proposal_pending → accepted
不适事件：任何 running 状态 → paused；后端提案 blocked
姿态丢失：短缺口不计数；超过 500ms 重置阶段

确认版本：必须匹配当前 input_version，否则 409

摘要请求示例

{
  "session_id": "demo-001",
  "input_version": 1,
  "exercise": "squat",
  "source": "simulation",
  "reps": 8,
  "active_seconds": 60,
  "observable_seconds": 55,
  "form_events": 1,
  "fatigue": 8,
  "discomfort": false,
  "target_reps": 12,
  "persist": false,
  "profile": {"weight_kg": 65, "experience": "beginner", "goal": "habit"}
}

exercise：动作目录 id，正式核心为 squat/jumping_jack，其余实验；source：simulation/camera/video；fatigue：0–10。observable_seconds 不得大于 active_seconds。数值范围以 schema 为准。身高、体重与示意外观参数由用户填写，原创演示骨架不测量人体，也不使用官方 SMPL 参数。

可选 rep_details（默认空，最多 100 条）为深蹲单次记录，字段：number、start_seconds、bottom_seconds、end_seconds、descent_seconds、ascent_seconds、min_angle_degrees、rom。rom 为 within_rule/below_rule/unobservable，只代表实验幅度规则。时间为不含暂停的活动时钟；阶段差值必须一致，次数递增、不重叠且位于本组时长以内。开合跳暂不接受此字段。结果回传用于复盘、trace 与保存。

响应包含 coverage、completion、energy、proposal、trace、saved。energy 是 gross_scenario_estimate：含静息的演示假设范围，不是统计区间。proposal 状态 pending/blocked/accepted/rejected。

确认 body：{"input_version":1}。不存在的当前会话 404；重复／旧版本更新、旧版本确认、不适禁止继续均 409；schema 不合法 422。accept 幂等地返回已确认状态，不自动启动摄像头或运动。

2026-10-21：新增 /api/sessions/{id}/reject，body 同 accept；支持 proposal_id（推荐随 input_version 一并发送，兼容旧调用时可省）。当前 ID 为 session_id:input_version。响应记录 decided_at；同一终态重复提交幂等，已接受不能改拒绝，已拒绝不能改接受；旧版本或错误提案身份 409。浏览器采用同样状态规则和按 session 查询的解释，不再从全局最近报告解释其他会话。

摘要新增成对的 work_seconds/rest_seconds，非负有限且和不得超过 observable_seconds；总时钟不含暂停。未提供分段的旧摘要仅使用可观察深蹲完整周期，其余标未知，不用次数估时。energy 新增 available/unknown_seconds，数值仅覆盖已分类片段；无已分类片段时 available=false，界面显示无法估算而不是零消耗。两端共享参数和黄金样例。

数据边界与离线说明

2026-10-22 算法评测增加主动同意的关键点内存记录，默认关闭；仅记录坐标、可见性、画面比例和训练时钟，不记录原始影像或自动上传。用户可撤回勾选并清空记录，重置/换视频/关闭页面也会清空；手动导出的本地 JSON 由用户管理，删除本机摘要不会删除已下载文件。详见 标注与回放规范。

当前默认行为

  • 摄像头只申请 video，不申请 audio。画面只到浏览器和同源 Worker，不传后端。
  • 关键点仅前端内存。后端接收次数、时长、质量事件、体重、疲劳、不适以及最近 100 次深蹲的阶段时间、最低角度与实验幅度状态等摘要。新增单次数据仍可能属于敏感健康信息，遵循同一保存选择。
  • persist=false 默认不写 SQLite；内存报告最多 100 条，进程结束消失。保存是用户主动选择。
  • SQLite 在 data/sessions.sqlite3，Git 忽略。历史读取最多 50 条。
  • 删除清空本机摘要表和内存报告；当前不声称物理安全擦除，SQLite 或文件系统残留应由系统磁盘保护处理。
  • JSON 导出由用户点击执行；导出的文件属于用户管理，可能包含健康摘要。
  • 默认不使用第三方分析脚本、云端追踪或运行时 CDN。仅 assets=online 显式在线资源模式允许下载公共模型/WASM；Worker 和主线程采用相同策略，不上传原始视频。可选语言模型仅回环地址，不接受远程 URL。
  • 本机原有会议纪要忽略且不上传；任何新增访谈和用户原始记录单独保管。

本原型的部署边界

默认回环、单机单用户原型，没有账号权限、TLS、公网攻击防护、多租户隔离或数据库加密实现。不要直接把服务监听 0.0.0.0 发布为多人健康平台。远程服务化应另设计认证、数据授权、存储、删除和运维边界。
