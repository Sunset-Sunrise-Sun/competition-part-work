LocalFit Agent：参赛方案与可行性分析

版本：0.1 · 记录日期：2026-10-09 · 时区：Asia/Shanghai

这份文档用于团队记录、展示和方案交流。赛事事实来自官网，技术能力来自官方文档；架构、里程碑和验收数字是项目建议。代码实现状态以 README 和 VALIDATION 为准，不能把规划项视为已完成。

1. 结论与项目定位

全流程健康教练适合赛道一，但原始设想包含动作识别、卡路里、不同体型、多模态、饮食、动作纠正、端侧隐私等多个高难度方向。参赛版应收敛为面向居家健身新手的端侧 AI 教练，核心是：离线动作纠正＋基于训练表现调整计划；饮食是闭环补充，广泛健康管理属于赛后路线。

一句话：在普通笔记本上，通过摄像头理解动作、结合用户反馈调整训练，不上传原始音视频，完成训练前、训练中、训练后的指导。

首批用户建议是校园中希望在宿舍或家里运动、缺少训练经验的成年人。这一人群便于访谈和真实试用。先证明用户能完成训练、理解提示和计划调整，再扩大人群。

团队约束已确认：4–5 人，主要偏算法和网页全栈；普通笔记本＋摄像头演示，可用 4090 服务端开发和 A100 训练；2026-10-31 前提交。

2. 总体赛事要求

官网：第四届开放原子大赛·2026 开源行业解决方案创新赛。赛道一是“开源基础软件与解决方案”，面向基础软件、AI 工具链、智能体框架、行业及数据平台，不限定技术栈，强调场景落地。软件形式的 LocalFit 与该定位匹配；这是选题判断，不代表官方资格审核结果。

官网列明团队不超过 8 人、负责人 1 名；报名对象为企业、高校实验室、科研机构、开源社区、行业联合体。需先落实报名主体，不自行假定个人学生团队可直接报名。提交可运行仓库、介绍文档（推荐 PDF）和核心功能演示视频，材料打包按审核邮件指引发至 bjoscc@oschina.cn，截止 10 月 31 日 24:00。入围名单 11 月 6 日，线下决赛 11 月 13 日，北京亦庄通明湖会议中心。官网结果公布日期有当日／次日两种文字，以通知为准。

赛道一与二评审：技术创新 30%，场景落地 30%，开源治理 20%，长期发展 20%。官网明确简单堆砌现成工具得分较低。项目需要用可复现证据解释，相比固定视频教程、固定训练计划或单纯聊天助手，有什么实际改进。

4. 动作技术路线

先从侧面深蹲和正面开合跳开始。用户先选择动作，系统识别动作阶段、次数和质量，降低开放式识别难度。

处理链：关键点 → 时间平滑 → 视角与可见性检查 → 动作阶段状态机 → 次数 → 可观察偏差 → 带依据提示。

MediaPipe Pose Landmarker 输出 33 个人体关键点及可见性，支持网页视频。它不是动作纠正引擎，纠错需要自己设计与验证。检测同步调用可能阻塞主线程，采用 Web Worker。单目三维估计不能当作精密运动测量。

侧面深蹲可观察幅度、节奏、躯干倾斜趋势；膝内扣更依赖正面。每个机位限定评价能力。提示应表达证据，例如“本组下降幅度比校准动作小”，避免仅给不透明综合分。

“不同体型”通过躯干等比例尺度归一化、个人初始基线、训练历史体现，不从视频推断真实体重或身体健康。校准本身可能不规范，不能自动当作正确动作标准。需区分机位偏差、遮挡、模型误差与动作问题；按体型、衣着、光照报告验证结果。

当前代码是规则基线：深蹲左侧髋膝踝角度的双阈值计数、可见性门控、倾斜提示；开合跳按手臂和脚距状态计数。自动机位判断与个体校准尚未完成。关键点可见性不是纠错正确率。

有足够标注和明确错误模式后可训练小型 TCN/GRU 时序模型，对比规则基线；ONNX Runtime Web 端侧部署。按用户划分训练、验证、测试集，避免同人相邻片段泄漏。

5. 消耗估算与饮食

基础公式：总消耗 kcal ≈ Σ MET × 体重 kg × 时长小时。按运动和休息分段，标记是否含静息消耗；如输出净活动消耗，应另作计算和明确说明。动作识别帮助选择活动类别，节奏、自评强度可形成估算情景，但没有数据不能宣称动作幅度准确预测能量。

Compendium 官方指出 MET 表不是为了精确测量个体活动能耗而设计；个体能耗、静息代谢存在差异。范围应标“假设下的情景范围”，没有统计校准不能称 95% 置信区间。无间接测热等真值，不报卡路里预测准确率。参考：定义、个体限制。

当前代码 MET 值是演示假设，不是完整活动条目映射。后续需每个动作绑定来源 ID、活动描述、参数版本和适用条件。

饮食先做手动食物选择＋确认克数＋数据库计算。可研究 USDA FoodData Central，补充中国食物、烹饪与配方覆盖；记录食品 ID、来源、每 100g 营养、版本和使用许可。模型只解释查表结果，不编造数值。不把运动消耗机械等价为可多吃多少。一般建议可引用 WHO 健康饮食资料。当前 4 条食物数值是未核验演示条目，不提供完整饮食处方。

6. 架构与算力安排

推荐浏览器实时感知＋同机 FastAPI Agent 服务。React/TypeScript/Vite 页面、Canvas 骨架、MediaPipe Worker、动作状态机、结构化摘要、本地 SQLite。主界面不等待语言模型逐帧决策。

普通笔记本是最终验收设备：姿态、计数、纠错、计划调整必须本地可完成。4090 用于开发、模型评测和较大模型对照；A100 用于有价值的小模型训练，不必为用算力训练大模型。若 4090 远程运行并接收摘要，该模式必须另标远程增强，不能称全部端侧。

可选 llama.cpp＋量化中文小模型，先试 Qwen3-4B，再根据实际速度和内存缩小。当前适配器仅连接同机回环地址、只解释已有结果，不执行计划。模型权重不提交 Git。LangGraph 适合混合确定性与模型步骤，作为后续替换当前轻量编排器的实现项。

7. 多 Agent 协作

角色 输入 输出与权限
主教练 目标、档案、状态 调度、提出整体计划
训练分析 次数、质量、节奏、问题 带依据的表现摘要
计划调整 摘要、疲劳、历史 下一组／下次计划提案
饮食 食物、份量、偏好 查表结果与一般建议
报告 结构化分析与提案 可追踪复盘
停止规则 按钮、停止指令、不适 直接暂停，优先于建议

多个角色可以共享一个模型，不必分别常驻大模型。组间与训练后调度，训练／饮食独立任务可并行，但普通笔记本推理需根据内存和竞争顺序执行。

流程：用户确认初始计划 → 动作引擎实时运行 → 组末形成摘要 → 分析／饮食 → 计划提案 → 规则校验 → 用户确认 → 保存摘要 → 下次读取历史。用户主动报告疲劳比单独表情推断更适合作为初期输入。

输出包含 session_id、输入版本、时间戳、证据、建议与执行状态。主教练统一提交，旧版本拒绝，避免多 Agent 同时改计划。停止按钮直接影响前端运行状态，不等待后端。展示协作结果而非模型内部思维。

当前实现角色为 training_analyst、plan_adapter、safety_gate、reporter，确定性串行执行；饮食计算独立 API，尚未进入完整协作图。端侧 LLM 只作可选解释。该状态必须在展示中说明。

8. 网页与可交互性

四视图：训练准备／实时训练、复盘、饮食与历史、项目协作。准备页包括计划、机位覆盖、校准状态；训练页包括骨架、阶段、次数、一个最重要提示、开始／暂停／结束和疲劳反馈；复盘页展示问题时间线、完成度、估算依据、调整提案；饮食页允许修正份量和食物。

训练布局建议左侧画面＋骨架，右侧次数和教练提示，下方感受与隐私设置。协作记录显示分析完成、提案生成、检查通过、等待确认，点击看摘要和证据。避免同时播报多个角色。后续加入节奏曲线和历史趋势；本框架先保留清晰数值和 trace。

隐私必须可验证：本地模型与脚本、无运行时 CDN、原始帧默认内存、摘要保存需选择、删除与导出、关闭云端遥测。骨架与健康摘要仍敏感，去掉视频不等于匿名。网页能缓存不代表所有模型已离线准备；必须做断网重启全流程。

9. 分工、步骤与验收

角色 A 算法：姿态、状态机、纠错、校准、评测；B 后端/Agent：状态、工具、存储、本地模型；C 前端：摄像头、骨架、主流程；D 全栈/产品：饮食、报告、集成；E（可选）测试、数据、文档和视频。四人时 E 工作分摊，明确材料负责人。

10/9–11：报名主体、访谈、范围、设备摸底、一个动作闭环；10/12–16：两个动作、门控、纠错、页面；10/17–21：Agent、计划、饮食、历史；10/22–25：用户验证、对比和修复；10/26–28：冻结、复现、视频和文档；10/29–31：提交及缓冲。五天内动作引擎不稳定则保留两个动作，推迟增强项。

建议招募 8–12 位知情同意成年人做原型验证。计数报告每组 MAE，清晰机位下争取 ≤1 次；纠错分问题报告精确率、召回率和误报；个体校准对比固定规则；性能固定设备与分辨率报告有效分析帧率、P95 延迟与内存；遮挡／出画／错误视角能停止不可靠评价；Agent 对比固定计划、单 Agent、多 Agent 的约束满足率与调整合理性；离线断网重启并检查外部请求。数字是目标，不能当作实测值。详见 EVALUATION。

10. 创新、开源与路演

三个重点：带质量门控的个体校准纠错；训练证据到计划调整的可解释闭环；普通笔记本离线完成能力。分别配基线对比、协作决策证据、设备指标与断网记录，不自行宣称模型创新或 SOTA。

开源治理需 LICENSE、依赖与模型清单、贡献指南、Issue/PR 模板、启动文档、模型准备校验和可复现评测。原创代码、模型权重、食品数据、演示材料各核对许可。真实用户数据默认不入仓库。可用明确授权或合成数据。

演示主线：档案 → 校准/机位 → 训练计数 → 可观察偏差 → 纠正 → 主动疲劳反馈 → Agent 调整 → 用户确认 → 复盘与饮食 → 断网继续。视频时长本赛道官网未给固定限制，可准备约 3–5 分钟版本并以审核邮件为准。名称 LocalFit Agent / 本地健身教练，全面健康教练是长期路线。

当前不是 LangGraph 实现，不包含模型角色间自主对话。采用轻量确定性基线便于验证接口、冲突规则和交互。后续把节点移入 LangGraph StateGraph，保持 API 合同。

模块边界

  • 摄像头原始帧仅在浏览器主线程与同源 Worker 间传递，不发送后端。
  • Worker 只提取姿态；动作引擎独立可测试，不依赖 React。
  • 前端累计实际活动时长与最近有效姿态覆盖时长；暂停不计时；长时间追踪丢失重置动作阶段，避免跨缺口计数。
  • 后端仅接收有限字段摘要，不接收视频、音频或关键点数组。
  • 规则协作形成候选计划；用户确认才能更新目标；不适提案禁止确认。
  • LLM 仅解释已有提案，不能写状态。异常或未启用时用规则解释降级。
  • 默认同机单用户、单进程。没有认证、多人隔离或跨进程锁，不可直接暴露公网。

状态与合同

训练状态：ready → running ↔ paused → summarized → proposal_pending → accepted
不适事件：任何 running 状态 → paused；后端提案 blocked
姿态丢失：短缺口不计数；超过 500ms 重置阶段
摘要版本：新会话 1；同 session 更新必须严格递增
确认版本：必须匹配当前 input_version，否则 409

阈值和 500ms 是当前实验规则，待评测优化。当前 UI每次复盘生成新 session_id；API 也支持同会话版本更新。已保存报告可从历史读取；重启后不会恢复内存中的待确认提案，避免意外执行旧计划。

目标架构增强

加入档案与校准服务、训练历史检索、经核验食品库和引用、语音事件、LangGraph 编排、性能采样与回放评测。训练与饮食可以并行处理，但计划提交单点仲裁。每节点设截止时间、输出 schema、重试上限和降级路径；低置信度不得生成强纠错。

性能安排

渲染与推理解耦；当前前端约每 80ms 请求一次帧，单帧在途，Worker 同步 CPU 推理。不同笔记本实际帧率未知。训练中不调用 LLM；模型解释在组末按需运行。后续考虑 GPU 后端、输入降采样和帧耗时统计，先保留可比较的 CPU 基线。

部署形态

开发：Vite 5173 代理 API → 127.0.0.1:8000。单服务本地展示：先准备模型并构建网页，再启动／重启后端，FastAPI 将 frontend/dist 挂载在根路径，API 与网页同源，打开 8000。静态挂载在 API 路由之后，不遮挡 OpenAPI。Vite preview 仅静态预览，不代理 API。最终可封装桌面启动器。远程 GPU 模式单独标识数据边界，不算同机端侧。

算法与闭环评测方案

以下是待执行方案，不是已取得的真实精度。当前自动化测试证明逻辑约束，不证明人体动作模型泛化。

数据与划分

初步邀请 8–12 位知情同意成年人，覆盖不同身高、体型、衣着、光照与摄像头距离。每动作录制正常、未完成、暂停、出画、遮挡等情况，避免要求用户故意做危险动作。取得视频存储与使用选择；标注者审阅计数和问题，原始资料不入 Git。

按用户划分调参、验证、最终测试，禁止同人邻近片段随机分散到训练测试。小样本结果只支持原型结论。标准计数与纠错定义由有训练经验者审阅，标注分歧记录后裁定。

API 与数据合同

摘要请求示例

{
  "session_id": "demo-001",
  "input_version": 1,
  "exercise": "squat",
  "source": "simulation",
  "reps": 8,
  "active_seconds": 60,
  "observable_seconds": 55,
  "form_events": 1,
  "fatigue": 8,
  "discomfort": false,
  "target_reps": 12,
  "persist": false,
  "profile": {"weight_kg": 65, "experience": "beginner", "goal": "habit"}
}

exercise：squat/jumping_jack；source：simulation/camera；fatigue：0–10。observable_seconds 不得大于 active_seconds。数值范围以 schema 为准。体重由用户填写，不由视频推断。

响应包含 coverage、completion、energy、proposal、trace、saved。energy 是 gross_scenario_estimate：含静息的演示假设范围，不是统计区间。proposal 状态 pending/blocked/accepted。

确认 body：{"input_version":1}。不存在的当前会话 404；重复／旧版本更新、旧版本确认、不适禁止继续均 409；schema 不合法 422。accept 幂等地返回已确认状态，不自动启动摄像头或运动。

饮食请求

[{"food_id":"rice","grams":150},{"food_id":"egg","grams":50}]

当前 food_id：rice/egg/milk/broccoli，每次最多 100 条。响应明确 data_status=illustrative_unverified。正式食品条目必须增加数据库 ID、来源与版本。该接口当前不保存饮食历史。

将来 WebSocket 约定

尚未实现。实时计数不需要每帧发网络请求；未来仅将阶段摘要、用户指令和有限状态推送编排器。事件必须含 session_id、event_id、输入版本与事件时间，去重后处理。禁止未经范围评估增加原始视频上传。

数据边界与离线说明

当前默认行为

  • 摄像头只申请 video，不申请 audio。画面只到浏览器和同源 Worker，不传后端。
  • 关键点仅前端内存。后端接收次数、时长、质量事件、体重、疲劳与不适等摘要。
  • persist=false 默认不写 SQLite；内存报告最多 100 条，进程结束消失。保存是用户主动选择。
  • SQLite 在 data/sessions.sqlite3，Git 忽略。历史读取最多 50 条。
  • 删除清空本机摘要表和内存报告；当前不声称物理安全擦除，SQLite 或文件系统残留应由系统磁盘保护处理。
  • JSON 导出由用户点击执行；导出的文件属于用户管理，可能包含健康摘要。
  • 不使用第三方分析脚本、云端追踪或运行时 CDN。可选语言模型仅回环地址，不接受远程 URL。
  • 本机原有会议纪要忽略且不上传；任何新增访谈和用户原始记录单独保管。

本原型的部署边界

默认回环、单机单用户原型，没有账号权限、TLS、公网攻击防护、多租户隔离或数据库加密实现。不要直接把服务监听 0.0.0.0 发布为多人健康平台。远程服务化应另设计认证、数据授权、存储、删除和运维边界。

离线准备与验收

首次需要下载安装包、MediaPipe 权重与 WASM；可选 LLM 权重也提前准备。脚本会记录下载来源与哈希，但未独立验证发布方签名。

  1. 在线完成依赖和模型准备，构建／启动并确认资源加载成功。
  2. 关闭全部 LocalFit 页面与服务，断网，再重新启动本地前后端。
  3. 浏览器打开本地地址，模拟和真实摄像头分别走完训练、反馈、复盘、确认。
  4. 开发工具 Network 记录请求；应只访问本机资源和 API。可选 LLM 请求发生在后端回环。
  5. 未选择保存时检查无新记录；选择后读历史，再删除。
  6. 保存设备、模型、commit、网络记录和失败场景。开发热更新会访问本机 WebSocket，不等于云端上传。

浏览器缓存、页面里“本地”文字、无视频上传接口不能独自证明完整离线。尚未做完上述步骤前，用“设计支持离线，验收待完成”。

安装、启动与故障处理

环境

Node.js 22.12+；Python 3.11+（本次机器是 Python 3.14）；支持摄像头的现代 Chrome/Edge。仅本机 localhost，普通笔记本性能需要实测。

Windows 从 README 的两终端命令启动。macOS/Linux 把 .venv\Scripts\python.exe 换成 .venv/bin/python。后端锁文件是本次实测版本；若其他平台需变更依赖，记录并更新测试。

摄像头资产

在 frontend 执行 npm ci、npm run prepare:models，生成 /public/models/pose_landmarker_lite.task、manifest 及 /public/wasm 运行文件。脚本固定模型 URL 与 npm 包版本，记录 SHA-256，权重不入 Git。没有可达下载网络时在有网络的设备准备后复制这些文件夹，并校验 manifest。许可复核见 DEPENDENCIES。

摄像头失败：检查浏览器权限、其他程序占用、是否用 localhost 安全上下文；模型失败检查 /models 和 /wasm 请求是否返回文件而不是 HTML。当前模型 Worker CPU 基线可能较慢，不保证所有浏览器均通过。

可选同机 LLM

安装官方 llama.cpp，选择并核对中文模型/量化权重。在本机回环启动兼容 /v1/chat/completions 的服务（常用端口 8080）。启动后端前设置：

$env:LOCAL_LLM_ENABLED = 'true'
$env:LOCAL_LLM_URL = 'http://127.0.0.1:8080'

.env.example 只是示例，本代码不会自动加载 .env。网页复盘点击“查看解释”。未启用直接用规则文本；超时或服务异常降级。当前未捆绑或自动启动 LLM，不宣称已经测过具体权重。只允许回环 URL，禁止凭据和重定向。

常见问题

  • 网页服务待启动：检查 8000 服务和 Vite proxy，后端 /api/health。
  • 端口占用：确认不是队友已有服务，选其他端口时同步 Vite 代理和 CORS。
  • 计划不调整：观察不足（覆盖率 <0.6 或活动 <10s）时保持，查看 trace；阈值是待验证规则。
  • 重启后不能确认旧报告：待确认状态只在进程内，重新训练，不恢复执行旧提案。
  • 模型下载被代理阻断：配置所在终端的网络代理；不要把代理凭据写入仓库。
  • 单服务展示：准备模型后 npm run build，重启后端，打开 8000；后端在启动时检查 dist 是否存在。
  • vite preview：只作静态预览；完整 API 联调请用 dev 或后端单服务。

架构决策记录

ADR-001：先交付训练闭环（2026-10-09）

背景：4–5 人，约三周提交，多模态原设想范围过大。

决策：两个动作＋质量门控＋反馈＋计划确认是 P0；表情、照片份量、语音、自训模型按完成程度延期。

后果：能积累可验证核心证据；覆盖范围有限，展示必须说明。

ADR-002：实时规则与慢速 Agent 分离

决策：计数、暂停、质量门控在浏览器规则层；Agent 组间与组末处理。所有计划调整经过规则和用户确认。

后果：LLM 故障不阻塞训练；模型只能解释／提出受约束提案，不能逐帧自由指挥。

ADR-003：确定性协作作为首个可运行基线

决策：v0.1 使用轻量 Python 编排器，四角色结构化 trace；LangGraph 后续接入，API 不变。

后果：降低基础框架成本，但不能宣称已完成自主多智能体或 LangGraph。用对比实验判断引入模型协作的收益。

ADR-004：同机端侧与远程增强分开

决策：笔记本完成核心；4090 与 A100 开发训练；同机 LLM 可选。权重和资源提前准备。

后果：纯离线演示有清晰数据边界；远程模式后续需独立说明。

ADR-005：Markdown 源文档＋独立 HTML 展示

决策：团队日常维护 Markdown，在 GitHub Review；导出无外部依赖 HTML 用于交流和打印。

后果：便于共同版本管理；PDF 手动打印后不作为主源，每次生成从 Markdown 同步。
