# LocalFit Agent：参赛方案与可行性分析

版本：0.1 · 记录日期：2026-10-09 · 时区：Asia/Shanghai

这份文档用于团队记录、展示和方案交流。赛事事实来自官网，技术能力来自官方文档；架构、里程碑和验收数字是项目建议。代码实现状态以 README 和 VALIDATION 为准，不能把规划项视为已完成。

## 1. 结论与项目定位

全流程健康教练适合赛道一，但原始设想包含动作识别、卡路里、不同体型、多模态、饮食、动作纠正、端侧隐私等多个高难度方向。参赛版应收敛为面向居家健身新手的端侧 AI 教练，核心是：**离线动作纠正＋基于训练表现调整计划**；饮食是闭环补充，广泛健康管理属于赛后路线。

一句话：在普通笔记本上，通过摄像头理解动作、结合用户反馈调整训练，不上传原始音视频，完成训练前、训练中、训练后的指导。

首批用户建议是校园中希望在宿舍或家里运动、缺少训练经验的成年人。这一人群便于访谈和真实试用。先证明用户能完成训练、理解提示和计划调整，再扩大人群。

团队约束已确认：4–5 人，主要偏算法和网页全栈；普通笔记本＋摄像头演示，可用 4090 服务端开发和 A100 训练；2026-10-31 前提交。

## 2. 总体赛事要求

官网：[第四届开放原子大赛·2026 开源行业解决方案创新赛](https://www.oschina.net/oa2026/)。赛道一是“开源基础软件与解决方案”，面向基础软件、AI 工具链、智能体框架、行业及数据平台，不限定技术栈，强调场景落地。软件形式的 LocalFit 与该定位匹配；这是选题判断，不代表官方资格审核结果。

官网列明团队不超过 8 人、负责人 1 名；报名对象为企业、高校实验室、科研机构、开源社区、行业联合体。需先落实报名主体，不自行假定个人学生团队可直接报名。提交可运行仓库、介绍文档（推荐 PDF）和核心功能演示视频，材料打包按审核邮件指引发至 bjoscc@oschina.cn，截止 10 月 31 日 24:00。入围名单 11 月 6 日，线下决赛 11 月 13 日，北京亦庄通明湖会议中心。官网结果公布日期有当日／次日两种文字，以通知为准。

赛道一与二评审：技术创新 30%，场景落地 30%，开源治理 20%，长期发展 20%。官网明确简单堆砌现成工具得分较低。项目需要用可复现证据解释，相比固定视频教程、固定训练计划或单纯聊天助手，有什么实际改进。

## 3. 功能可行性与范围

| 设想 | 判断 | 本次范围 |
|---|---|---|
| 动作识别、计数 | 高 | 必做 2 个动作，稳定后扩展第三个 |
| 动作纠正 | 中高，依赖机位与遮挡 | 限定可观察问题；识别不足时不下判断 |
| 不同体型 | 中，需要验证 | 比例归一化、初始校准、个体基线 |
| 卡路里预测 | 估算可行，精准预测困难 | 情景范围、依据、总／净消耗标记 |
| 自适应计划 | 高 | 完成度＋质量＋主观反馈形成闭环 |
| 语音交互 | 中高 | 短句指令，始终保留按钮 |
| 表情识别疲劳 | 不确定性大 | 延后，不作为疼痛或疾病判断依据 |
| 饮食指南 | 基础版可行 | 手动记录、确认份量、查表与一般建议 |
| 照片算热量 | 份量、油脂和配方难推断 | 延后，可作为食物候选辅助 |
| 全流程离线 | 核心闭环可行 | 本地训练与计划优先，再扩展语言能力 |

MVP 必做：档案、训练计划、机位提示、姿态、计数、限定纠错、暂停、不适反馈、训练摘要、计划确认、历史与删除。增强：语音、校准、经核验食物库、小型时序模型。延后：表情健康推断、全面医疗管理、照片自动份量和大规模模型训练。

## 4. 动作技术路线

先从侧面深蹲和正面开合跳开始。用户先选择动作，系统识别动作阶段、次数和质量，降低开放式识别难度。

处理链：关键点 → 时间平滑 → 视角与可见性检查 → 动作阶段状态机 → 次数 → 可观察偏差 → 带依据提示。

[MediaPipe Pose Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/web_js) 输出 33 个人体关键点及可见性，支持网页视频。它不是动作纠正引擎，纠错需要自己设计与验证。检测同步调用可能阻塞主线程，采用 Web Worker。单目三维估计不能当作精密运动测量。

侧面深蹲可观察幅度、节奏、躯干倾斜趋势；膝内扣更依赖正面。每个机位限定评价能力。提示应表达证据，例如“本组下降幅度比校准动作小”，避免仅给不透明综合分。

“不同体型”通过躯干等比例尺度归一化、个人初始基线、训练历史体现，不从视频推断真实体重或身体健康。校准本身可能不规范，不能自动当作正确动作标准。需区分机位偏差、遮挡、模型误差与动作问题；按体型、衣着、光照报告验证结果。

当前代码是规则基线：深蹲左侧髋膝踝角度的双阈值计数、可见性门控、倾斜提示；开合跳按手臂和脚距状态计数。自动机位判断与个体校准尚未完成。关键点可见性不是纠错正确率。

有足够标注和明确错误模式后可训练小型 TCN/GRU 时序模型，对比规则基线；ONNX Runtime Web 端侧部署。按用户划分训练、验证、测试集，避免同人相邻片段泄漏。

## 5. 消耗估算与饮食

基础公式：总消耗 kcal ≈ Σ MET × 体重 kg × 时长小时。按运动和休息分段，标记是否含静息消耗；如输出净活动消耗，应另作计算和明确说明。动作识别帮助选择活动类别，节奏、自评强度可形成估算情景，但没有数据不能宣称动作幅度准确预测能量。

Compendium 官方指出 MET 表不是为了精确测量个体活动能耗而设计；个体能耗、静息代谢存在差异。范围应标“假设下的情景范围”，没有统计校准不能称 95% 置信区间。无间接测热等真值，不报卡路里预测准确率。参考：[定义](https://pacompendium.com/)、[个体限制](https://pacompendium.com/corrected-mets/)。

当前代码 MET 值是演示假设，不是完整活动条目映射。后续需每个动作绑定来源 ID、活动描述、参数版本和适用条件。

饮食先做手动食物选择＋确认克数＋数据库计算。可研究 USDA FoodData Central，补充中国食物、烹饪与配方覆盖；记录食品 ID、来源、每 100g 营养、版本和使用许可。模型只解释查表结果，不编造数值。不把运动消耗机械等价为可多吃多少。一般建议可引用 WHO 健康饮食资料。当前 4 条食物数值是未核验演示条目，不提供完整饮食处方。

## 6. 架构与算力安排

推荐浏览器实时感知＋同机 FastAPI Agent 服务。React/TypeScript/Vite 页面、Canvas 骨架、MediaPipe Worker、动作状态机、结构化摘要、本地 SQLite。主界面不等待语言模型逐帧决策。

普通笔记本是最终验收设备：姿态、计数、纠错、计划调整必须本地可完成。4090 用于开发、模型评测和较大模型对照；A100 用于有价值的小模型训练，不必为用算力训练大模型。若 4090 远程运行并接收摘要，该模式必须另标远程增强，不能称全部端侧。

可选 llama.cpp＋量化中文小模型，先试 Qwen3-4B，再根据实际速度和内存缩小。当前适配器仅连接同机回环地址、只解释已有结果，不执行计划。模型权重不提交 Git。LangGraph 适合混合确定性与模型步骤，作为后续替换当前轻量编排器的实现项。

## 7. 多 Agent 协作

| 角色 | 输入 | 输出与权限 |
|---|---|---|
| 主教练 | 目标、档案、状态 | 调度、提出整体计划 |
| 训练分析 | 次数、质量、节奏、问题 | 带依据的表现摘要 |
| 计划调整 | 摘要、疲劳、历史 | 下一组／下次计划提案 |
| 饮食 | 食物、份量、偏好 | 查表结果与一般建议 |
| 报告 | 结构化分析与提案 | 可追踪复盘 |
| 停止规则 | 按钮、停止指令、不适 | 直接暂停，优先于建议 |

多个角色可以共享一个模型，不必分别常驻大模型。组间与训练后调度，训练／饮食独立任务可并行，但普通笔记本推理需根据内存和竞争顺序执行。

流程：用户确认初始计划 → 动作引擎实时运行 → 组末形成摘要 → 分析／饮食 → 计划提案 → 规则校验 → 用户确认 → 保存摘要 → 下次读取历史。用户主动报告疲劳比单独表情推断更适合作为初期输入。

输出包含 session_id、输入版本、时间戳、证据、建议与执行状态。主教练统一提交，旧版本拒绝，避免多 Agent 同时改计划。停止按钮直接影响前端运行状态，不等待后端。展示协作结果而非模型内部思维。

当前实现角色为 training_analyst、plan_adapter、safety_gate、reporter，确定性串行执行；饮食计算独立 API，尚未进入完整协作图。端侧 LLM 只作可选解释。该状态必须在展示中说明。

## 8. 网页与可交互性

四视图：训练准备／实时训练、复盘、饮食与历史、项目协作。准备页包括计划、机位覆盖、校准状态；训练页包括骨架、阶段、次数、一个最重要提示、开始／暂停／结束和疲劳反馈；复盘页展示问题时间线、完成度、估算依据、调整提案；饮食页允许修正份量和食物。

训练布局建议左侧画面＋骨架，右侧次数和教练提示，下方感受与隐私设置。协作记录显示分析完成、提案生成、检查通过、等待确认，点击看摘要和证据。避免同时播报多个角色。后续加入节奏曲线和历史趋势；本框架先保留清晰数值和 trace。

隐私必须可验证：本地模型与脚本、无运行时 CDN、原始帧默认内存、摘要保存需选择、删除与导出、关闭云端遥测。骨架与健康摘要仍敏感，去掉视频不等于匿名。网页能缓存不代表所有模型已离线准备；必须做断网重启全流程。

## 9. 分工、步骤与验收

角色 A 算法：姿态、状态机、纠错、校准、评测；B 后端/Agent：状态、工具、存储、本地模型；C 前端：摄像头、骨架、主流程；D 全栈/产品：饮食、报告、集成；E（可选）测试、数据、文档和视频。四人时 E 工作分摊，明确材料负责人。

10/9–11：报名主体、访谈、范围、设备摸底、一个动作闭环；10/12–16：两个动作、门控、纠错、页面；10/17–21：Agent、计划、饮食、历史；10/22–25：用户验证、对比和修复；10/26–28：冻结、复现、视频和文档；10/29–31：提交及缓冲。五天内动作引擎不稳定则保留两个动作，推迟增强项。

建议招募 8–12 位知情同意成年人做原型验证。计数报告每组 MAE，清晰机位下争取 ≤1 次；纠错分问题报告精确率、召回率和误报；个体校准对比固定规则；性能固定设备与分辨率报告有效分析帧率、P95 延迟与内存；遮挡／出画／错误视角能停止不可靠评价；Agent 对比固定计划、单 Agent、多 Agent 的约束满足率与调整合理性；离线断网重启并检查外部请求。数字是目标，不能当作实测值。详见 EVALUATION。

## 10. 创新、开源与路演

三个重点：带质量门控的个体校准纠错；训练证据到计划调整的可解释闭环；普通笔记本离线完成能力。分别配基线对比、协作决策证据、设备指标与断网记录，不自行宣称模型创新或 SOTA。

开源治理需 LICENSE、依赖与模型清单、贡献指南、Issue/PR 模板、启动文档、模型准备校验和可复现评测。原创代码、模型权重、食品数据、演示材料各核对许可。真实用户数据默认不入仓库。可用明确授权或合成数据。

演示主线：档案 → 校准/机位 → 训练计数 → 可观察偏差 → 纠正 → 主动疲劳反馈 → Agent 调整 → 用户确认 → 复盘与饮食 → 断网继续。视频时长本赛道官网未给固定限制，可准备约 3–5 分钟版本并以审核邮件为准。名称 LocalFit Agent / 本地健身教练，全面健康教练是长期路线。
